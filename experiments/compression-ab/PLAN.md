# 압축 보조 모델 A/B 실험 계획

메인 모델 `Qwen3.6-35B-A3B-8bit` 고정.
컨텍스트 압축(`auxiliary.compression`)을 누가 하느냐만 바꾼다.

| 조건 | 요약 모델 | config |
|---|---|---|
| **A** | 메인이 직접 (35B 8bit) | `auxiliary.compression.provider: auto` |
| **B** | gemma-4-12B-it-OptiQ-4bit | `provider: omlx` + `model: gemma-4-12B-it-OptiQ-4bit` (현행) |

**판정 대상은 요약문 자체가 아니라, 압축을 3~4번 거친 뒤 나오는 최종 아웃풋의 품질이다.**

작성 2026-08-03 · 대상 `~/.hermes/hermes-agent/agent/context_compressor.py`

---

## 0. 사전 확인 결과 (1단계 실측)

| 항목 | 값 |
|---|---|
| GPU wired limit | 57344MB (56GB) |
| Qwen3.6-35B-A3B-8bit | 35GB, **VLM** (`vision_config` 있음 → `auxiliary.vision` 분리 불필요) |
| gemma-4-12B-it-OptiQ-4bit | 8.4GB, 컨텍스트 131072 |
| 현행 메인 4bit-DWQ | 19GB (텍스트 전용) |
| 압축 발동점 | 262144 × 0.35 = **91.7K 토큰**, 압축 대상 ≈60K |
| 코퍼스 | `state.db` 44,874 메시지 / 최대 세션 571KB(≈140K 토큰) |
| 8bit 프리필 | 13.7K/6.4s · 55K/45.3s · 137.7K/314.1s |
| oMLX 동시 요청 | **`max_concurrent_requests: 1`** — 압축 중 메인은 대기 |
| 메모리 가드 | `prefill_memory_guard: true`, tier `balanced` |

### ⚠️ 초안의 "메모리는 병목이 아니다"는 틀렸다

가중치 합(35 + 8.4 = 43.4GB < 56GB)만 보고 여유 12.6GB로 판단했으나,
실제로는 **프리필 헤드룸**이 제약이다. 8bit 상주 중 gemma에 큰 프롬프트를 보내면:

```
oMLX prefill memory guard rejected this prompt:
Prefill would require ~46.73 GB peak (current 45.21 GB + KV+SDPA 1.53 GB)
but dynamic ceiling is 44.24 GB … static cap is 58.00 GB
but only 0 B is reclaimable right now
```

**게다가 비결정적이다** — 동일한 요청이 실패한 직후 성공했다.
`dynamic ceiling`이 시스템의 다른 앱 상황에 따라 움직이기 때문이다.

이것이 실험의 성격을 바꾼다. 가드에 걸리면 hermes는 400을 받고
`_fallback_to_main_for_compression()`으로 **조용히 메인에 넘긴다**.
즉 "gemma로 압축 중"이라고 믿는 동안 실제로는 메인이 압축하고,
실패 왕복 시간까지 얹힌다. `max_concurrent_requests: 1`이므로 그 시간은
통째로 사용자 대기 시간이다.

→ **측정 항목 추가: 메모리 가드 발동률** (`probe_guard.py`).
   실제 압축 대상 크기 60K에서 gemma가 대부분 튕기면
   조건 B는 품질을 재기도 전에 신뢰성으로 탈락이다.

→ 판정 기준은 **속도 이득 vs 누적 품질 손실 vs 신뢰성** 세 축이 된다.

### 그 밖에 1단계에서 확인된 것

- **thinking 제어**: `chat_template_kwargs`를 요청 본문 **최상위**에 둬야 먹는다.
  `extra_body`로 한 겹 감싸면 oMLX가 무시한다 (1.95s `finish=length` → 0.31s `finish=stop`).
  hermes의 `auxiliary.<task>.extra_body`는 최상위로 펼쳐 보내므로 설정 방식 자체는 맞다.
- **조건 A는 thinking이 켜진 채로 압축한다** (현행 `auxiliary.compression.extra_body: {}`).
  8bit 메인은 "1+1은? 숫자만"에도 512토큰을 thinking에 쓰고 `finish=length`로 답을 못 냈다.
  이것이 조건 A의 예상 약점이며, 실험은 이 상태 그대로 잰다 —
  그게 `provider: auto`로 뒀을 때 실제로 벌어지는 일이기 때문이다.
  A가 thinking 때문에 진다면 "A + thinking OFF"는 결과를 본 뒤 별도로 다룬다.
- **프롬프트 캐시가 실재한다**: SSD 캐시 185GB, `preserve_mid_system_cache: true`.
  고유 텍스트 + `cached_tokens` 확인 둘 다 필수.

## 1. 실험의 핵심: 세대 연쇄(generation chain)

코드가 실제로 하는 일:

```
G1 압축 → 요약₁                          (first-compaction 프롬프트)
요약₁ + G2 → 압축 → 요약₂                (iterative-update 프롬프트, :1345)
요약₂ + G3 → 압축 → 요약₃
요약₃ + G4 → 압축 → 요약₄
```

`self._previous_summary = summary` (`:1404`) 때문에 **모델은 자기가 쓴 요약을 다시 입력받는다.**
3세대쯤이면 입력의 대부분이 원본 대화가 아니라 자기 출력이다.
iterative 프롬프트가 요구하는 것도 단순 요약이 아니라 상태 기계 조작이다 —
번호 목록 이어가기, `In Progress` → `Completed Actions` 이동, 답변된 질문을 `Resolved`로 이동.

**1회 요약만 재는 실험은 이 누적 열화를 통째로 놓친다. 그래서 4세대까지 돌린다.**

## 2. 설계

### 2-1. 통제

같은 원본 구간 G1~G4를 A와 B에 동일하게 먹인다.
요약이 갈라지면서 2세대부터 입력이 달라지는데, **그 갈라짐 자체가 측정 대상**이다.

결정적으로 — **최종 아웃풋 생성은 양쪽 다 메인 8bit가 한다.**
그래야 "답변자 능력 차이"가 아니라 "요약 품질 차이"만 남는다.

```
[조건 A] 요약₄(8bit가 만듦) ──┐
                              ├──→ 메인 8bit가 답변 생성 ──→ 채점
[조건 B] 요약₄(gemma가 만듦) ─┘
```

### 2-2. 상한선 기준점

A/B 두 조건에 더해 **무압축(ceiling)** 을 한 번 돌린다.
원본 G1~G4 전체를 메인 8bit에 그대로 주고 같은 질문을 시킨다.
이건 세 번째 비교군이 아니라 **척도의 100% 지점**이다 —
"압축을 아예 안 했으면 얼마나 잘했을까" 대비 A와 B가 각각 몇 %인지 표현하기 위한 것.
이게 없으면 "A 62점 B 58점"이 큰 차이인지 오차인지 알 수 없다.

### 2-3. 조건 B는 모델 스왑을 동반한다

8bit(35GB) + gemma(8.8GB)를 동시에 올리면 ceiling 56GB에서 프리필 헤드룸이
남지 않아 가드가 요청을 거부한다. 그러니 하나는 내려야 한다.
러너는 압축 전후로 명시적으로 언로드/로드하고, **그 시간을 조건 B의 비용에 계상한다.**

1단계 실측 (`probe_swap.py`):

| 항목 | 시간 |
|---|---|
| 8bit 언로드 | 0.3s |
| gemma 로드 | 5.8s |
| 8bit 재로드 | 9.0s (oMLX 자체 추정 22.3s보다 빠름) |
| **스왑 왕복** | **≈15s** — 조건 A는 0s |

**프롬프트 캐시는 스왑을 넘어 살아남는다** (스왑 후 `cached=28,672`, 15.3s → 4.8s).
oMLX SSD 캐시 185GB가 실제로 동작하므로, 스왑 비용은 로드 시간뿐이고
재프리필까지 얹히지는 않는다.

> ⚠️ 실제 hermes는 언로드를 호출하지 않는다. 지금 config 그대로 두면
> gemma 압축이 가드에 걸려 400 → 조용히 메인 폴백이다.
> 조건 B를 실제로 쓰려면 별도 조치(oMLX 축출 정책 또는 훅)가 필요하며,
> 이 사실 자체가 REPORT의 결론에 들어가야 한다.

### 2-4. 전제가 하나 무너졌다 — gemma가 더 느리다

| 같은 30K 프리필 | 시간 |
|---|---|
| Qwen3.6-35B-**A3B** 8bit | **15.3s** |
| gemma-4-12B-4bit | **25.3s** |

Qwen3.6-35B-A3B는 MoE라 활성 파라미터가 3B뿐이고 40레이어 중 10개만
full attention이다. gemma-4-12B는 dense 12B다. **이름의 35B는 총 파라미터지
연산량이 아니다.** "작은 모델이니 빠르다"는 전제가 성립하지 않는다.

→ 질문이 뒤집힌다. "gemma가 빠른 대신 품질이 떨어지나?"가 아니라
**"gemma는 스왑 15s까지 얹고 압축도 더 느린데, 품질이 그걸 만회하나?"**

### 2-5. 두 트랙 (세대 크기로 나눈다)

초안은 `config_context_length=32768`로 낮춰 축소 재현하려 했으나 두 군데서 막혔다:

1. `threshold_tokens`는 `MINIMUM_CONTEXT_LENGTH`(64,000) 하한에 걸려 안 내려간다
2. 더 나쁜 건 `max_summary_tokens = min(context × 0.05, 12000)`이라
   **요약 예산이 12,000 → 1,638로 쪼그라든다**

요약 예산은 `budget = clamp(입력토큰 × 0.20, 2000, max_summary_tokens)`인데,
예산이 하한 2,000에 눌리면 두 모델이 똑같이 짓눌려 **차이가 드러나지 않는다.**
특히 thinking이 켜진 8bit에 불리해 조건 A가 부당하게 지는 실험이 됐을 것이다.

그래서 컨텍스트는 운영값(262144)으로 두고 **세대 크기만** 조절한다.

**트랙 1 — 주 실험 (4세대)**
- 세대 20K rough × 4세대, 코퍼스 2건 × 조건 2개 = 압축 16회
- 요약 예산 약 2,500~4,000 (운영 12,000보다 작음 — 트랙2로 교차 검증)
- 세대마다 프로브 채점 → **열화 곡선**

**트랙 2 — 실크기 검증 (2세대)**
- 세대 55K rough × 2세대 → 요약 예산 8,000~12,000으로 **운영과 같은 대역**
- 코퍼스 1건 × 조건 2개 = 압축 4회

### 2-6. 코퍼스 (2건, 확정)

`pick_corpus.py`로 크기·중복도·user 발화 분포·사실 밀도를 함께 봤다.

| 코퍼스 | 세션 | 성격 | 고유도 | 경로 | 숫자 |
|---|---|---|---|---|---|
| **vault** | `20260723_202332_7c4e67` | Obsidian 볼트 정리 (코드 작업형) | 1.00 | **336** | 250 |
| **rivian** | `20260720_230652_441de6` | Rivian R2 분석 (미해결 종료형) | 1.00 | 3 | **458** |

> 함정 기록: 처음 고른 `20260607_203813_442a5f`(571KB, 최대 세션)는 실제로
> **고유도 0.21**이었다. 같은 web_search 결과 4,721자가 29번 반복 저장돼 있었고,
> 끝에 붙은 "returned the same result 28 times / 29 times" 카운터 때문에
> md5가 전부 달라 정확 해시 검사를 그대로 통과했다. 숫자를 정규화한 뒤에야 걸렸다.
> 이걸로 실험했으면 압축이 부당하게 쉬워져 결론이 틀렸을 것이다.

## 3. 채점: 최종 아웃풋 종합 분석

### 3-1. 프로브 5종 (세대마다 반복 → 열화 곡선)

각 세대의 요약만 주고 메인 8bit에게 묻는다. 정답은 원본 전체에서 미리 추출해 고정.

| # | 프로브 | 무엇을 재나 |
|---|---|---|
| P1 | "지금 무슨 작업 중이고 다음 단계는?" | 재개 능력. `## Active Task` 생존 |
| P2 | "G1에서 나온 특정 파일·수치는?" | **초기 세대 정보 생존 — 누적 열화의 직격 지표** |
| P3 | "왜 X 대신 Y를 택했나?" | `Key Decisions`와 그 이유 생존 |
| P4 | "중간에 취소된 작업은?" | reverse signal 처리 |
| P5 | "아직 답 못 받은 질문은?" | `Pending User Asks` 생존 |

P2가 가장 중요하다. 1세대에는 A·B 둘 다 맞히고 3~4세대에서 갈리는 게 예상 시나리오이고,
**어느 세대에서 무너지는가**가 이 실험의 답이다.

### 3-2. 최종 종합 과제 (4세대 요약 기준, 1회)

프로브는 단답이라 "문서로서 쓸 만한가"를 못 잰다. 그래서 마지막에 실제 산출물을 만들게 한다.

> "이 인수인계 문서를 근거로, 작업을 이어받는 사람에게 줄 다음 단계 계획을 쓰고
> 첫 단계를 실제로 수행하라."

산출물을 원본 전체를 아는 기준으로 종합 채점한다:
- 사실 정확도 (지어낸 파일·명령·수치 건수)
- 다음 단계의 타당성 (이미 끝난 일을 다시 시키는가)
- 놓친 블로커 (원본에 있던 미해결 문제를 모르는가)
- 무압축 상한선 대비 상대 점수

### 3-3. 자동 지표 (매 세대, 사람 판단 없음)

| 지표 | 실패의 의미 |
|---|---|
| 섹션 12개 존재 | 템플릿 붕괴 |
| `Completed Actions` 항목 수 추이 | **PRESERVE 위반 — 세대가 갈수록 줄면 정보 소실 중** |
| 번호 연속성 | iterative 지시 미준수 |
| 파일 경로 보존율 (원본 대비) | 이어받기 불가 |
| 한글 비율 / 비-한글 CJK 혼입 수 | 4bit 다국어 모델의 알려진 결함 |
| 비밀값 잔존 (`sk-`, `ghp_` 등) | **단독 탈락 사유** |
| 출력 토큰 ≤ `max_summary_tokens` | 압축이 압축이 아님 |
| `_summary_model_fallen_back` | **True면 그 실행 무효** (gemma 재는 줄 알고 메인 잼) |

`Completed Actions` 항목 수 추이가 열화의 조기 경보다. 세대마다 늘어야 정상인데 줄면 잊고 있는 것.

### 3-4. 속도

- 세대별 압축 소요 시간, 4세대 누적
- gemma 콜드 로드 페널티 1회 별도 측정

## 4. 함정 대비 (지난 실측에서 실제로 결론을 뒤집었던 것들)

| 함정 | 대비 |
|---|---|
| **순서 효과** — 두 번째가 항상 느림 | 세대 단위 교대 `A₁,B₁,A₂,B₂,…`. A 전부→B 전부 금지 |
| **프롬프트 캐시** — 불가능한 tok/s | 매 호출 `usage.prompt_tokens_details.cached_tokens` 확인, `!=0`이면 **자동 무효** |
| **조용한 폴백** | 매 호출 후 `_summary_model_fallen_back` 확인 |
| **콜드/웜 혼재** | 조건별 워밍업 1회 후 버림. 콜드 비용은 별도 항목 |
| **tok/s 함정** | 중간 지표 대신 **4세대 누적 소요 시간** |
| **채점 오염** | 정답표·프로브는 **실행 전에 확정**해 파일로 고정. 요약을 본 뒤 만들지 않는다 |
| **축소 편향** | 트랙 2(실크기)로 교차 검증 |

## 7. 판정 규칙 (실행 전에 확정)

결과를 보고 기준을 정하면 원하는 답이 나온다. 미리 못 박는다.

- **gemma(B) 채택**: 4세대 누적 시간이 A의 절반 이하이고 **동시에**
  4세대 종합 과제 점수가 A의 90% 이상, 그리고 P2(초기 정보 생존)가 3세대까지 유지
- **auto(A) 채택**: 위 미달, 또는 B에서 **비-한글 CJK 혼입·비밀값 누출·폴백이 1건이라도** 발생
- **차이 없음**: 두 조건의 종합 점수 차가 코퍼스 2건 간 변동폭 안에 들면
  → 운영이 단순한 **auto**를 택한다 (모델 하나 덜 상주시키는 쪽)
- **둘 다 탈락**: 무압축 상한선 대비 A·B 모두 60% 미만이면
  모델 문제가 아니라 `threshold`/`target_ratio` 문제다 → 설정 재조정으로 방향 전환
