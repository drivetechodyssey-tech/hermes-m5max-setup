01가장 큰 문제 — curator가 거꾸로 돌고 있었다

Hermes의 curator는 주 1회 돌며 안 쓰는 스킬을 정리하는 백그라운드 작업입니다. 그런데 소스(agent/curator.py)를 보니 판정 기준이 last_activity_at 하나뿐이고 use_count는 전혀 참조하지 않습니다.

구조적 결함

“30회 썼지만 최근 90일간 안 씀” == “0회 쓰고 방치됨”

영상 제작처럼 프로젝트 단위로 몰아 쓰는 패턴에서는, 잘 쓰던 스킬일수록 프로젝트 사이의 공백 때문에 삭제 대상이 됩니다. 직관과 정반대로 작동합니다.

복구 경로도 잘못 안내되고 있었다

curator 리포트는 ~/.hermes/skills/.archive/에서 복구하라고 안내하는데 그 디렉토리는 실제로 생성되지 않습니다. 진짜 복구본은 .curator_backups/*/skills.tar.gz에만 있고, backup.keep: 5 + 주 1회 실행이라 5주치만 보존됩니다. 그 이전에 삭제된 25개는 영구 유실됐습니다.

조치

14개 복구 (내용이 다른 스킬로 흡수된 것은 중복을 피해 제외) · 31개 핀 고정(pinned=true는 자동 패스와 LLM 패스 모두 건너뜀) · stale_after_days 30→120 · archive_after_days 90→365 · backup.keep 5→12(약 3개월치)

02프롬프트 예산 — 어디가 진짜 비만인가

“스킬이 많아서 느리다”가 흔한 직관입니다. 실측해보니 세 번째로 중요한 요인이었습니다.

원인

기본 설정이 지나치게 관대했습니다. tool_output.max_bytes: 50000(≈12,500토큰), file_read_max_chars: 100000(≈25,000토큰) — 툴 하나가 컨텍스트의 1/5을 먹을 수 있게 열려 있었습니다.

세 가지 레버의 실제 효과

레버절감비고
① 툴 출력 상한 50000→16000, 100000→40000 가장 큼대화 내용의 86%를 차지하던 원인을 직접 차단
② 미사용 툴셋 비활성화 tts, image_gen, delegation 2,171 토큰delegate_task 하나가 1,728토큰인데 전 기간 3회 사용
③ 스킬 다이어트 45개 비활성화 1,016 토큰4,089 → 3,073 토큰

03작업이 중간에 끊기고 있었다

agent.max_turns가 10으로 설정돼 있었습니다. 기본값은 90입니다. 실제로 문제였는지 세션 데이터로 확인했습니다.

04메모리가 아니라 시간이 컨텍스트를 결정한다

기존 README는 “131K 컨텍스트 = 63GB, 위험”이라고 적고 있었습니다. 이 숫자가 맞는지 확인하려고 모델 config.json을 열었더니 일반적인 KV 캐시 공식이 이 모델엔 통하지 않는다는 걸 발견했습니다. 

full_attention_interval: 4
layer_types: [linear, linear, linear, full, linear, linear, linear, full, ...]
num_hidden_layers: 40   →   full_attention은 10개뿐

Qwen3.6은 하이브리드 어텐션입니다. 40개 레이어 중 10개만 full attention이고, 나머지 30개는 linear_attention(Mamba 계열)이라 시퀀스 길이와 무관하게 상태 크기가 고정입니다. 컨텍스트에 비례해 자라는 건 10개뿐이므로, 40레이어로 계산한 기존 값은 4배 과대추정이었습니다.

실측

178,000 토큰을 처리하는 동안 프로세스 메모리가 19.9GB → 20.1GB로 사실상 변하지 않았습니다. 64GB에서 이 모델의 메모리는 어떤 컨텍스트에서도 제약이 아닙니다.

상한은 열되, 압축 발동점은 고정

compression.threshold는 컨텍스트 상한에 대한 비율입니다 (threshold_tokens = context_length × threshold). 그래서 상한만 올리면 압축 발동점도 함께 밀려나 “183K까지 쌓아두고 매번 4분씩 다시 읽는” 최악이 됩니다.

설정이전이후효과
model.max_tokens131,072262,144모델 최대치까지 여유 확보
compression.threshold0.70.35비율을 낮춰 상쇄
실제 압축 발동점91,75091,750변화 없음 — 평소 동작 동일

05모델 교체 — 4bit → 4bit-DWQ

DWQ(Distilled Weight Quantization)는 양자화된 가중치가 원본 모델의 출력을 따라가도록 증류 학습시킨 것입니다. 구조·크기·비트폭이 같으니 연산량은 그대로고 가중치 값만 개선됩니다.

교체 시 반드시 확인할 것

DWQ는 비전 가중치가 빠진 텍스트 전용 빌드입니다. vision_config도 preprocessor_config.json도 없고, oMLX가 engine: batched / type: llm으로 인식합니다(기존 4bit는 vlm). 메인을 DWQ로 쓰려면 auxiliary.vision을 VLM으로 반드시 따로 지정해야 합니다.

06보조 모델 — 크기가 아니라 thinking이 문제였다

Hermes는 12개 부수 작업(제목 생성, 승인 판단, 압축, 비전 등)에 각각 다른 모델을 지정할 수 있습니다. provider: auto는 메인 모델을 뜻합니다. “가벼운 일엔 작은 모델”이 자연스러운 발상이지만, 측정해보니 문제가 다른 데 있었습니다.

설정소요토큰결과

“제목을 5단어로” 같은 요청에 1,500토큰 15초를 쓰고도 답을 못 냅니다. reasoning 모델이라 짧은 작업에서 추론에 예산을 다 쓰기 때문입니다. auxiliary.<task>.extra_body가 이걸 제어하는 통로였습니다. 

auxiliary:
  title_generation:
    extra_body:
      chat_template_kwargs:
        enable_thinking: false

07검토했지만 켜지 않은 것

최적화 후보를 다 켜는 게 답은 아닙니다. 두 기능은 측정 결과 끄는 게 맞았습니다.

chunked_prefill — 이득 0, 페널티 3% OFF 유지

문서가 이득의 조건을 명시합니다 — “Reduces TTFT for concurrent requests at the cost of per-step overhead.” 그런데 이 서버는 max_concurrent_requests: 1이라 끼워넣을 다른 요청이 없습니다.

설정측정값 (40K 프리필, 3라운드 교대)중앙값
OFF25.2 / 26.0 / 26.3초26.0초
ON26.7 / 26.7 / 27.1초26.7초

중앙값 차이는 3%로 작지만 ON 3개가 모두 OFF 3개보다 높아 범위가 겹치지 않습니다. 우연이라기엔 일관적이고, 문서가 말한 오버헤드와 정확히 일치합니다.

specprefill — 속도가 아니라 정확도를 거래하는 기법 OFF 유지

DEFAULT_KEEP_RATE = 0.20   → 프롬프트 토큰의 80%를 버림
DEFAULT_THRESHOLD = 8192   → 8K 넘는 프롬프트마다 발동
  • 평균 프리필이 6만 토큰이라 거의 매 호출 발동해 대부분을 버립니다.
  • draft 모델은 타깃과 토크나이저를 공유해야 하는데 Qwen3.6 계열에 8B 이하 모델이 존재하지 않습니다(HF 전수 확인).
  • 논문의 7.66× 개선은 Llama-3.1-405B 기준입니다. Qwen3.6-35B-A3B는 활성 파라미터가 3B인 MoE라 타깃 자체가 이미 싸서 경제성이 정반대입니다.
  • 프롬프트 캐시 적중률이 93%라 최적화하려는 전체 프리필 자체가 드뭅니다.

로그 회전 — mv로 하면 안 되는 이유

config.yaml의 logging.max_size_mb는 Python 로거가 쓰는 agent.log에만 적용됩니다. gateway.error.log는 launchd가 StandardErrorPath로 직접 리다이렉트하는 파일이라 규칙 밖이고 무한정 자랍니다.

핵심 제약

게이트웨이 프로세스가 이 파일을 fd=2로 붙들고 있습니다. mv로 옮기면 프로세스는 이동된 inode에 계속 쓰므로 새 파일은 영영 비어 있습니다. 그래서 copytruncate — 내용을 복사한 뒤 원본을 제자리에서 비웁니다(: > file). fd가 유지되어 재시작 없이 회전됩니다.

rotate-logs.sh + 사용자 레벨 launchd 에이전트(매일 04:00, sudo 불필요)로 구성했고, 회전 후 inode 유지 · offset 0부터 정상 기록 · 세대 밀어내기 · KEEP=3 정리를 모두 확인했습니다.

09측정하면서 틀렸던 것들

이 작업에서 네 번 잘못된 결론에 도달했다가 재측정으로 뒤집었습니다. 모두 “그럴듯한 숫자”를 만들어내는 종류라 검증 없이는 걸러지지 않습니다.

잘못된 결론원인실제
“DWQ 프리필이 2배 느리다” 순서 효과 — 두 번째로 도는 모델이 항상 느림(발열·드리프트) 교대 측정하니 1.03배, 노이즈 범위
“4bit 프리필 91,385 tok/s” 프롬프트 캐시 적중 — 같은 텍스트 재사용 고유 텍스트로 재측정 시 1,782 tok/s
“131K는 63GB로 위험” 하이브리드 어텐션 미반영 — 40레이어로 계산 full attention은 10개뿐, 메모리는 제약이 아님
“8bit는 tool call을 못 한다” 응답이 reasoning 도중 200토큰에서 잘림 예산을 늘리니 정상 동작
그래서 얻은 측정 원칙

① 교대 측정(A,B,A,B)으로 드리프트를 상쇄한다  ·  ② 매 측정마다 고유 텍스트를 쓰고 cached_tokens == 0을 확인한다  ·  ③ tok/s 같은 중간 지표가 아니라 “과제를 끝내는 데 걸린 총 시간과 토큰”을 본다

실제로 tok/s가 낮은 모델이 과제 완료는 42% 빨랐습니다. 중간 지표만 봤다면 정반대 결론을 내렸을 겁니다.
